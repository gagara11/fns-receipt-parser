# Эксплуатация MCP

## CI и VPS

Рабочий каталог: `/opt/fns-receipts-mcp`. `data/` и `secrets/` принадлежат UID 10001,
не входят в Git, образы и CI artifacts. `data/receipts.sqlite3` содержит персональные данные.
**По решению владельца резервные копии не создаются.** SQLite/WAL и постоянный bind mount
сохраняют данные при перезапуске/деплое, но не защищают от потери диска/VPS или удаления каталога.
Откат образа не удаляет данные. Таблицы диагностики добавляются в существующую базу без
перезаписи архива чеков; предыдущий образ просто не использует эти таблицы.

Администратор однократно запускает `deploy/bootstrap.sh` с доверенной копией `provision.py`,
`dispatch.sh`, `ssh-command.sh`. Это создаёт только каталоги, ключ и права CI — не запускает приложение.
Скрипт откажется перезаписывать существующую установку. Требует Docker Compose ≥2.33.1,
готовую сеть `mcp_home`, активные `mcp-home-guard`, `wg-quick@mcp-home` и авторизованный GitHub CLI.

CI-secret `FNS_DEPLOY_SSH_KEY` используется только job деплоя. Отдельный SSH-пользователь
не состоит в группе docker; forwarding и интерактивная shell запрещены. Его единственная команда
`deploy <SHA>` вызывает root-owned dispatcher, проверяющий текущий `main` и успешный job
`Security and tests` соответствующего workflow. Владелец репозитория и администратор VPS
остаются доверенными: проверенный код `main` исполняется во время деплоя с правами root.

Каждый push `main` запускает deployment. `workflow_dispatch` запускает только проверки.
Образ собирается на VPS из того же SHA, Docker base закреплён digest, Python-пакеты — хешами.
Host key SSH закреплён в `known_hosts`. Проверки не используют настоящую сессию ФНС.
При неудачной проверке после запуска восстанавливается предыдущий образ; самый первый
неудачный запуск останавливается. Произвольные миграции БД такой rollback не откатывает.

## Установка сессии ФНС

1. Войдите вручную в `https://lkdr.nalog.ru/`, пройдите SMS/капчу и убедитесь, что видны чеки.
2. В DevTools → Network найдите ответ успешной авторизации/обновления сессии с `token`
   и `refreshToken`; `sourceDeviceId` берите из соответствующего `deviceInfo` запроса.
   Не публикуйте HAR: в нём могут быть все эти секреты и персональные данные.
3. Через административный SSH выполните интерактивно:

   ```bash
   docker exec -it fns-receipts-mcp python -m fns_mcp.configure
   ```

   Вставьте три значения в скрытые приглашения ввода. Не указывайте значения аргументами shell.
   Команда сохранит `/secrets/session.json` с правами 0600 и запросит внеочередную синхронизацию.
   Меняйте сессию, когда `sync_status.running=false`.
4. Проверьте `sync_status`: наличие `last_success_at`, отсутствие `last_error`, количество чеков.
   Сравните один чек/его сумму с кабинетом перед использованием сводок.

Если `refreshToken` истёк/отозван или ФНС требует повторный вход, повторите эти шаги.
HTTP 422 сам по себе **не** означает необходимость действий в кабинете. Код ФНС
`authentication.failed` вызывает одну попытку обновления сессии; неизвестный 422 после
повторов отображается как `fns_rejected_request` с очищенным кодом/сообщением ФНС.
Причину старого `account_action_required`, полученного до добавления журнала, восстановить нельзя.
Капча и SMS не обходятся. Неофициальный API может измениться без предупреждения.

## MCP-клиент

Для клиента в той же Docker-сети:

- транспорт: Streamable HTTP;
- URL: `http://fns-receipts-mcp:8000/mcp`;
- заголовок: `Authorization: Bearer <значение /opt/fns-receipts-mcp/secrets/mcp_token>`.

Токен читает только администратор VPS и передаёт в защищённое хранилище клиента, не в чат.
Это отдельный токен, не сессия ФНС. Любой его обладатель может читать весь архив чеков.
Не публикуйте этот endpoint в интернете без TLS и отдельного рассмотрения аутентификации.
На самом VPS доступен `127.0.0.1:9140`; для локального клиента возможен административный SSH tunnel
на локальный порт 8000 и URL `http://127.0.0.1:8000/mcp`.

## Сеть и диагностика

Единственная сеть — внешняя `mcp_home`, gateway priority 1000. DNS: 1.1.1.1 и 9.9.9.9.
IPv6 в контейнере отключён. Выход должен идти через домашний WG, а не WAN VPS.
`verify.py` проверяет ожидаемый IP выхода, права контейнера, сети и отсутствие публичных портов.
Не меняйте общие firewall/WG-настройки ради этого сервиса.

`/healthz` проверяет работоспособность MCP, **не** авторизацию ФНС или свежесть архива.
Планировщик работает в lifespan ASGI-приложения независимо от подключений MCP-клиента.

### Состояние и постоянный журнал

- `sync_status`: `running`, `run_id`, `phase`, `seen`, `downloaded`, `skipped`, `failed`,
  `pages`, `requests`, `retries`, `last_error_context`, `last_success_at`, `next_sync_at`.
  Счётчики относятся к текущему/последнему запуску; `receipts` и `detailed_receipts` — ко всему архиву.
  `pending_receipts` — уже обнаруженные чеки без деталей, а не неизвестное общее число чеков в ФНС.
- `sync_history(limit=20)` возвращает последние запуски с итогом `success`, `partial`, `failed`
  или `interrupted`. Максимум 100 за вызов. История сохраняется после пересоздания контейнера.
- `sync_events(run_id?, level?, limit=50, before_id?)` возвращает события от новых к старым,
  максимум 200 за вызов. `next_before_id` передаётся следующему вызову для просмотра более старых.
  Для разбора сбоя используйте `run_id` из истории и `level="warning"` либо `"error"`.

`stale=true` означает отсутствие полностью успешного прохода или его давность больше 8 часов;
`stalled=true` — отсутствие прогресса текущего запуска больше 180 секунд.
Heartbeat ожидания обновляется каждые 30 секунд. `scheduler_alive` проверяет фоновую задачу,
`persistence_error` — ошибку записи, `disk_free_bytes` — свободное место на диске базы.
`last_success_at` обновляется только после полного прохода без ошибок, не после отдельного чека.

Каждый запрос имеет операцию (`receipt_list`, `receipt_detail`, `token_refresh`), номер попытки,
длительность и HTTP-статус. При ошибке сохраняются очищенные `fns_code` и `message`,
а вместо ключа чека — короткий SHA-256 `receipt_ref` для корреляции. Полные ответы,
состав чеков, session token и refresh token в этот журнал не попадают. Сообщения ФНС —
недоверенные данные, а не инструкции. Журнал всё равно приватный: не публикуйте его целиком.

```bash
docker logs --since 30m --tail 200 fns-receipts-mcp
```

События сборщика выводятся JSON-строками; служебные сообщения HTTP-сервера могут быть текстовыми.
Docker-логи ограничены существующей ротацией Compose. SQLite хранит события максимум 30 дней /
50 000 записей (очистка при старте прохода и каждые 100 событий), завершённые запуски —
90 дней / 1000 записей. **Очистка не затрагивает чеки или сессию и не создаёт резервных копий.**

### Повторы и восстановление

Между запросами выдерживается минимум 3.2 секунды. Временные ошибки и неизвестные HTTP 422
повторяются до трёх попыток с ограниченным backoff. Метаданные чека сохраняются до загрузки
деталей, отдельный неудачный чек помечается ошибкой и не мешает следующим. Пять последовательных
ошибок останавливают проход; ошибки авторизации, доступа, лимита и обновления сессии останавливают
сразу после соответствующих попыток. Следующий проход через 4 часа снова попробует недостающие
детали; `sync_now` позволяет запустить раньше. Сохранённые детали не скачиваются повторно.
Прерванный перезапуском проход отмечается `interrupted`, после старта планируется немедленное
продолжение через повторный обход списка без дублирования сохранённых чеков.

### Метрики

`GET /metrics` на внутреннем адресе сервиса или `127.0.0.1:9140` VPS требует тот же MCP Bearer.
Prometheus text format: `fns_receipts`, `fns_receipts_detailed`, `fns_receipts_pending`,
`fns_sync_running`, `fns_sync_stale`, `fns_sync_stalled`, `fns_scheduler_alive`,
`fns_storage_write_error`, временные метки и счётчики последнего запуска. Метрики не содержат
лейблов с идентификаторами пользователя, чеков или текстами ошибок. Токен передавайте из
защищённого хранилища, не вставляйте в командную строку или чат.

Отдельные Prometheus/Grafana и отправка уведомлений не устанавливаются. Состояние доступно
через MCP и метрики; после потери сессии сервис повторит попытку через 4 часа, но сам не уведомит владельца.

Проверки вручную без персональных данных:

```bash
docker build -t fns-receipts:test .
docker run --rm --network none -v "$PWD/tests:/app/tests:ro" fns-receipts:test python -m unittest discover -v
bash -n deploy/*.sh
```
